## Решение и альтернативы

Использовать существующий monitoring manifest. Это решение
исполнителя в рамках поручения: не требуются новые сервисы, БД или изменения
админки. Простое включение старого manifest отвергнуто: его проверки допускают
ложный зелёный статус и небезопасный payment scenario. Прямой доступ админки к БД
Gems отвергнут: магазин остаётся источником каталога и бизнес-правил.

Мониторинг: frontend, backend, реальный PostgreSQL SELECT 1, Redis PING,
опубликованный и доступный каталог отдельно CS2/Rust/TF2, настройки цены Gems.
Период 300 секунд соответствует supplier sync. Snapshot и доступные предложения
должны быть свежими по принятому storefront порогу 15 минут; важен observed_at,
а не только завершение sync. Ошибки возвращают 503 и фиксированный код без
внутренних сообщений драйвера. Настройки цены проверяются как конфигурация,
не называются свежим FX и не изменяются.

Manifest отключает legacy browser scenarios, не объявляет synthetic scenarios
или неподдерживаемые recovery actions. Сохранённый signed payment endpoint
возвращает PAYMENT_SCENARIO_NOT_AVAILABLE без записи и зависимостей от Payments.
Подпись привязана к публичному API пути, телу и canonical timestamp ±5 минут.
Схема commerceEvents = 2 соответствует существующим payload; webhook/outbox
не включаются и исторические события не отправляются в рамках этой задачи.

Исследование инвойсов отложено до отдельного продолжения: native COINS/scale100,
все три игры, сохранение materialized previewSelection и правил цены. Сейчас
не добавлять endpoints, capability, профиль или тестовый PDF.

## Границы и приёмка

Не менять дизайн, клиентскую корзину, платежи, fulfillment, provider credentials,
курсы, markup, исторические инвойсы или данные соседних проектов. Не создавать
worktree/новый checkout. Публичные read-only health checks не требуют provisioning
нового integration secret. Runtime env и credentials сейчас не изменяются.

Приёмка: локальные unit/DB/contracts/lint/types/build, независимое ревью, CI и
deploy конкретного SHA, сохранённые monitoring runs из API и worker, админка в
браузере. Проверить отсутствие invoice capability/profile и неизменность
финансовых счётчиков. Реальная оплата остаётся недоступной до отдельной настройки
провайдера и реализации безопасного сценария; это не успех оплаты.
