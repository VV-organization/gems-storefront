# Рабочие скины на главной: план исправления

> Исполнение: superpowers:executing-plans, последовательно в текущем checkout. Коммит и push поручены пользователем после реализации; проверка на production следует после публикации.

**Цель:** карточки первого экрана и «Коллекции» показывают только реальные доступные товары с рабочим просмотром, страницей и добавлением в корзину.

**Основание:** запрос пользователя от 2026-11-05 и диагностика `home.tsx` → `presentationProducts`: отсутствующий товар заменялся объектом из дизайн-макета с нулевой ценой и заранее записанным slug.

**Решение:** сохранить исходные позиции нож/пистолет/винтовка и приоритет исходных marketHashName. Для каждой позиции выбрать доступный товар соответствующей категории. Если его нет в загруженных данных, запросить доступные товары этой категории. Не создавать товар из картинки. Пустая подборка скрывает товарные карточки, сохраняя заголовок и переход в каталог. Одна подборка используется в Hero и CollectionStage.

**Альтернативы:** скрывать только отсутствующие исходные скины проще, но первый экран может оставаться пустым при полном каталоге. Произвольные три товара ухудшают исходную композицию. Выбрана замена по категории, без изменения CSS и анимаций.

**Стек:** Node 24, Next.js 16, React 19, TypeScript, node:test, Playwright; существующий NestJS/PostgreSQL backend.

## Ограничения

- Сохранить Commissioner, CSS, assets, responsive, фон, композицию и анимации.
- Только серверные цена, availability, slug, revision и идентичность товара; не менять платежи, providers или выдачу.
- Изображение замены должно соответствовать замене; не накладывать старую картинку на другой товар.
- Никаких изменений соседних проектов, секретов, deployment и БД приложения.
- Destructive integration tests только через GEMS_TEST_DATABASE_URL, локальная gems_test с владельцем gems_test.
- Данные fixture и тесты UI не являются доказательством оплаты или выдачи.

## Особое внимание при проверке

1. Товар доступен, но не входит в первые 60 результатов: отдельный запрос категории на главной.
2. Сбой lookup или одной категории: сохранить остальные успешные ответы.
3. Нулевые/некорректные цены, unavailable, чужая игра, отсутствующее изображение: исключить из подборки.
4. 0–2 доступные категории: не дублировать товары и не создавать заглушки; не сломать мобильный вид.
5. Полный путь по каждой карточке, Escape/фокус, корзина после reload; отсутствие горизонтального overflow.

## Продолжение 2026-11-06: пустая подборка на production

После публикации 5465997 production-проверка выявила второй дефект: API каталога под нагрузкой превышал timeout, поэтому успешных данных для карточек не оставалось. Это расширяет первоначальное ограничение frontend-only: для устранения доказанной причины требуется изменение чтения backend и индексов БД, без изменения товарных/платёжных данных.

План исправления:

1. Убрать подсчёт всего каталога и построение фильтров из запросов подборки; добавить `/catalog/preview` и подключить SSR.
2. Ускорить выборку индексами порядка/категорий, убрать чтение большого JSON из supplier-фильтров; сохранить условия legacy-товаров.
3. Повторять временно неуспешное чтение один раз. Возвращать 404 только для ответа 404; для временной ошибки страницы товара показать повтор загрузки.
4. Проверить SQL на локальной тестовой БД, контракт, unit, lint/typecheck/build, весь E2E и сохранность дизайна.
5. После разрешённых пользователем commit/push дождаться деплоя, измерить живые ответы и проверить все три карточки, детали и корзину в существующей вкладке production.

Доказанная причина: `loadFacets` читал JSON specifications всего каталога (EXPLAIN ANALYZE 11,9 с); выборка трёх ножей занимала 3,4 с внутри БД. В браузере catalog-запросы завершались 500 через 30,4 с; SSR обрывал запрос через 5 с. Цена и доступность конкретных товаров отдельно возвращались корректно.

Исправление: item-only preview без count/facets; три частичных индекса и ANALYZE; supplier facets из исходного market hash name, legacy facets из прежнего JSON; unfiltered count без supplier/pricing joins; ограниченный retry чтения; error boundary с восстановлением вместо ложного 404.

Проверки до публикации: `npm run verify` — exit 0 (251 backend unit, 69 frontend unit, контракт, типизация, lint, build); integration — 165 passed, 1 внешний sandbox skipped. Регрессии preview и false-404 сначала воспроизведены падающими тестами. `visual:source`: 831 файл дизайна сохранён. Логи: `.local/home-skins-production/`.

Полный E2E: 63 passed, exit 0, включая временный 503 → экран ошибки → «Повторить» → успешная карточка и настоящий отсутствующий slug → 404. Независимое read-only ревью блокеров не выявило; производительность индексов проверяется отдельно после deployment на production-объёме.

Production после d00b9da: deployment и оба CI успешны; три последовательных SSR-загрузки вернули 3 карточки. В существующей вкладке проверены quick view и правильные страницы AK-47, Glock-18 и M9 без 404; M9 добавлен в гостевую корзину. Остаточная задержка общих страниц (до 10,7 с) разобрана EXPLAIN: planner ожидал 557 строк вместо 33 684 и сортировал весь каталог, выполняя 33 684 supplier lookup.
